# Контракт регистрации и входа

В рамках issue #10 определены HTTP-эндпоинты, DTO и правила валидации. Сохранение пользователя, проверка пароля и выдача токена относятся к задаче бизнес-логики. Единый формат ошибок и преобразование ошибок в HTTP-ответы относятся к отдельной задаче обработки ошибок API.

## Регистрация

`POST /auth/register`, JSON-тело:

```json
{
  "email": "ivan@example.com",
  "password": "secret123",
  "firstName": "Иван",
  "lastName": "Иванов"
}
```

Все поля обязательны. Email должен иметь допустимый формат и длину до 255 символов. Пароль содержит от 8 до 64 символов, хотя бы одну букву и одну цифру. Имя и фамилия &mdash; непустые строки длиной до 100 символов. Аватар пока не принимается.

Успешный ответ: `201 Created` с `userId`, `email`, `firstName` и `lastName`. Пароль в ответ не входит.

## Вход

`POST /auth/login`, JSON-тело с обязательными `email` и `password`. Проверяются формат email и заполненность пароля; правила сложности нового пароля при входе не применяются.

Успешный ответ: `200 OK` с `accessToken` и `tokenType`. Ожидаемое значение `tokenType` &mdash; `Bearer`.

## Статусы ошибок по контракту

| Статус | Условие |
| --- | --- |
| `400` | Отсутствует обязательное поле или тело запроса невозможно прочитать |
| `422` | Заполненное поле нарушает ограничения валидации |
| `401` | Неверные учётные данные при входе |
| `409` | Email уже занят при регистрации |

Описание этих статусов есть в Swagger. Их единый формат реализуется в задаче обработки ошибок API; проверка учётных данных и уникальности email &mdash; в задаче бизнес-логики.
